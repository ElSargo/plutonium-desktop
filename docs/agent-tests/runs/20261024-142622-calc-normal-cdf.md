## Problems

### 1. `read_window` on a freshly opened Calc document timed out, then LibreOffice crashed (tool bug, probably LibreOffice's accessibility crash underneath)

What happened:

- +48.7: Ctrl+N opened "Untitled 3" (#7, listed at +51.7).
- +54.9: `read_window {"window_id":7}` failed after 5.2 s with `org.freedesktop.DBus.Properties.GetAll timed out.` The helper log has the stack: `helper/src/dbus.ts:419`, the 5 s default `timeoutMs` in `call`, reached from `a11y.ts:247` (`GetAll` on `org.a11y.atspi.Accessible`).
- +62.2: the retry got `This thread has no window 7.`
- +64.1: `list_windows` showed only #8 "LibreOffice 26.8 Document Recovery", LibreOffice's crash-recovery dialog.
- The soffice.bin pid changed from 1103382 to 1106806, and the documents came back as #12–#14.

Evidence:

- **There's no core dump to read.** `coredumps.txt` says "none". `coredumpctl` has no soffice entry for 14:26–14:30. LibreOffice catches the fatal signal itself, saves for recovery and restarts (hence the recovery dialog), so systemd-coredump often never sees it.
- **The host's coredump log is flooded.** It's full of a `drkonqi-coredump-launcher` crash loop: about 1250 dumps in 14:25–14:30, already running at 14:00.

So the backtrace isn't available, and it isn't proven that `read_window` caused the crash. But nothing else was sent to the window between Ctrl+N and the crash. And the 2026-10-23 manual run caught `read_window` crashing Calc in `ScAccessibleContextBase::getLocale` twice. A `GetAll` that hangs for 5 s fits LibreOffice wedged inside an accessibility call.

What would tell:

- Rerun with LibreOffice's crash reporting on, or under `flatpak run --devel --command=gdb …`, and call `read_window` on a new Calc document within a few seconds of opening it.
- Alternatively, set `-env:UserInstallation` to a clean profile and check `…/user/crash/` for a dump.

Suggested fixes:

- When an AT-SPI call times out, `read_window` should say the app stopped answering, and should check whether the window still exists before returning. The agent had to work out the crash itself.
- If the getLocale crash is confirmed, consider skipping `Locale` (and any other property that triggers it) for LibreOffice. Reading per-property instead of `GetAll` on `Accessible` may avoid the property that aborts. Check this in `a11y.ts` against a reproduction.

Same as the 2026-10-23 known issue (`read_window` crashed Calc twice): still failing, as far as the evidence goes.

### 2. LibreOffice's menu and tooltip are drawn over the shell while its window isn't shown anywhere (user-visible glitch)

What happened:

- **The Insert menu.** At +147.8 the agent clicked "Insert" in the menu bar (`click_window 260,25`). LibreOffice's Insert menu appeared at the top left of the shell, over the sidebar and the thread's messages (frame `012856`; `x-012856.5` to `x-012900.5`). It stayed there until the agent's Escape at +153.4 (frame `012901`).
- **The Name Box tooltip.** Around +113, a "Name Box" tooltip showed over the sidebar (frame `y-012820`; also in the scan at about +140). It followed the agent's clicks on the Name Box at (120,225).
- **Where they were placed.** Both are where they'd be if the Calc window sat at the screen's origin. All the while, every window was `shown:false`: the user hadn't opened them, the panel was closed, and the thread was the selected one.

The agent couldn't see any of this: `snapshot_window` shows only the window itself. Nor did it say anything about it.

Likely cause: parked (unshown) windows are made transparent and click-through, and lifted to `kFloatingWindow` so that their popups show above the page (`ShellSurfaceBase::SetEmbedParked`, `chromium/patches/0001-…` around line 2795, `components/exo/shell_surface_base.cc`). Nothing hides the popups and menus of a parked window that no page is showing, so they're composited on top of the shell at the parked origin. Not confirmed in a debugger.

Suggested fix:

- While a window is parked and not shown by any page, keep its popup and menu children invisible (opacity 0, no event targeting), as the toplevel is.
- Alternatively, render them only into the agent's snapshot.

Also check that a grabbing popup on an unshown window can't take the user's pointer. `MaybeDismissGrabbingPopup` dismisses on a press outside, but here the user would be clicking an app they can't see.

Same as the 2026-10-23 known issue (a GTK context menu over the shell with the thread unfocused). It's still failing, and it happens with the thread focused too.

### 3. `launch_app` returns no windows after 1.3 s when the first window closes quickly (tool bug)

What happened: at +14.0, `launch_app` was given `wait_seconds: 30`. It returned `{"pid":1103271,"windows":[]}` at +15.3. The helper log says `pid 1103271's windows after 1.3 s:`, with an empty list. #1 "soffice" (pid 1103344, the short-lived oosplash/first soffice window) had appeared and gone again. Seconds later the splash (#2) and Recovery dialog (#3) were in the thread (+20.7).

The agent believed the opposite. It thought "No windows showed up after waiting 30 seconds" (frame `012652`) and reported "`launch_app` returned no windows even with wait_seconds: 30".

Cause: `launch` (`helper/src/daemon.ts:588`–`591`) breaks out of the wait as soon as `fresh.length > 0`. It sleeps 300 ms and returns `settled`, even if `settled` is now empty because the first window closed.

Suggested fix: if `settled` is empty, keep waiting until the deadline. Say in the result when windows came and went ("1 window opened and closed; still waiting…" or similar).

### 4. Name Box entry: `\n` inside `type_window` didn't commit, then keys seemed to stop working until Escape (agent mistake mostly; a timing problem in `type_window` possible, not confirmed)

What happened (all on #14):

- **+96.0:** `click_window 120,225` (the Name Box) and `type_window "A2:C1002\n"`, sent in parallel (both at 01:28:03.38–.39). The range wasn't selected (`seen/006` shows A2 only).
- **+100.7:** `click_window`, then `type_window "A2:A1002\n=ROW()-502"`, then `press_window alt+Enter`. The Name Box held `=ROW()-502` and the selection was still A2 (`seen/006`).
- **+109.3:** `ctrl+a`, `type "A2:A1002"`, `press Enter`. Nothing changed (`seen/007` is pixel-identical to `006`).
- **+116.4:** Escape. The Name Box reset to `A2` (`seen/008`).
- **+121.5 onwards:** click, `type_window` the range, a separate `press_window Enter`, then the formula, then `alt+Enter`. All four columns and ranges worked first time: `seen/009`–`011`, and the B1:C1002 selection at +147.2.

The `type_window` description covers this case:

> \n presses Enter; after an Enter that should move the focus (a toolbar box, a dialog field), click where the next text goes.

So typing the formula straight after `\n` in one call (+101.5) went against the description. Firing the first click and type in parallel (+96.0) is the agent's own race.

What's not explained is why `ctrl+a` / typing / Enter at +109 had no visible effect. The agent's guess, "stuck with Alt active", isn't supported by anything in the logs. A "soffice" window (#15) appeared during this stretch: there's a toast "soffice opened" from about +97 to +108 (frames `x-012805`–`x-012815`). The agent never listed windows here, so it didn't know about it. It may only have been the Name Box tooltip (Problem 2), or it may have been a LibreOffice message box (e.g. an invalid-name warning) that ate the keys until Escape. The helper log has no titles or times for #15 and #16.

What would tell:

- Have the helper log window titles and times.
- Test `type_window "A2:A1002\n"` alone, after a completed click, then snapshot. If it fails where `press_window Enter` works, `textKeys` needs a short pause after Enter (`keys.ts:58` maps `\n` to the same `Enter` code). That would make it a tool bug.

A small improvement either way: actions (`click_window`, `type_window`, `press_window`) could mention new windows of the thread that appeared meanwhile. `snapshot_window` shows the target window alone, so a dialog that's eating keys is invisible to the agent.
