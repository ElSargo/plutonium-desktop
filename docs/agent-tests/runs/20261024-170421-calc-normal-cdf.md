## Problems

### 1. `act_window` "select" on a chart-type list item: "The app refused to select it." (tool bug, on top of a toolkit limitation)

What happened:

- **+104.5:** `act_window {"window_id":8,"ref":"a26","action":"select"}` on the table cell "Line" in the Chart Type list. It failed in 0.0 s with "The app refused to select it."
- **+108.5:** `click_window` at the cell's center (535,333) selected Line (`seen/003`).

Cause:

- `select` (`helper/src/a11y.ts:707`) calls `Selection.SelectChild(index)` on the element's parent, here the `table` a9. It reports the `false` reply as a refusal (`ok()`, `a11y.ts:672`).
- The Flatpak LibreOffice uses the GTK3 VCL plugin, and this list is a two-column GtkTreeView (icon cell + text cell; read_window lists them in pairs).
- GTK3's tree-view accessible, `gtk_tree_view_accessible_add_selection`, returns FALSE for any view with more than one column. That is from memory of GTK3's `gtktreeviewaccessible.c`, not checked against this build.

So the tool asked correctly, and the toolkit declines. But the tool gives up where a click would have worked. The description promises "select (pick it in its list or tabs)", and the agent used it that way.

Suggested fix: when `SelectChild` returns false, or the parent has no Selection, fall back to a pointer click at the element's center (`{ click: point }`).

- Don't fall back to `DoAction`: these cells' only actions are "Expand or contract, Edit", and the `click` path (`CLICK_ACTIONS` → index 0) would run "Expand or contract".
- Say in the result that it clicked.

### 2. The agent never saw LibreOffice's "discard recovery data?" box, and misreported the recovery dialog as stuck (agent mistake; the tools gave no hint)

What happened:

- **+24.7:** Escape on the Recovery dialog (#2).
- **+35.2:** the `list_windows` sent with the Recover Selected click already showed a new **#3, title "", 524×160**. In run 20261024-170743 the same window (#3, 524×160) is LibreOffice's "Are you sure you want to discard the LibreOffice document recovery data?" (`seen/002` there). That's the answer to the Escape.
- **+37.4 and +41.1:** the agent read only #2. Both buttons were `(disabled)` (`seen/002`), most likely because the modal message box was up. It never read, snapshotted or mentioned #3.
- **+48.5:** Enter on #2 closed both. The documents appeared about 6 s later (+54.9). In between, `list_windows` returned `[]` once (+48.5).

The tester's report items 1–3 ("Escape did nothing", "no way to close", "windows briefly disappeared") all come from this. Escape worked: LibreOffice asked for confirmation.

The empty list is LibreOffice closing its dialogs before opening the recovered documents, not a tool fault.

Two smaller points:

- **The a11y click got past the modal box.** `act_window` click on "Recover Selected" (+35.2) ran the recovery while LibreOffice's modal box was open. A pointer click would have been blocked.
- **Suggested improvement:** action results (`press_window`, `click_window`, `act_window`) could name thread windows that opened meanwhile, e.g. "new window #3 (untitled, 524×160)". That would catch this and Problem 4 of the 20261024-142622 report.

### 4. `read_window` with a stale ref returns an empty string (tool bug, minor)

**+133.4:** `read_window {"window_id":7,"ref":"a4"}` returned `""`. The agent meant the wizard's Finish button: refs belong to a window, and a4 on #8 was Finish. But on #7, a4 was the status bar (first read, +71.5).

In chart mode the status bar object was evidently replaced. A defunct element renders as nothing (`a11y.ts:587` `if (node.defunct) return [];`), so the agent got an empty answer with no reason.

Suggested fix: for a ref read whose element is defunct, say "a4 is gone (the app replaced it): read the window again".

### 5. The shared LibreOffice profile still starts every run in crash recovery (app or environment: test harness)

- **What happened:** the run started with "Document Recovery" for Untitled 1–3. The agent recovered them, so 3 extra Calc windows were open all run, and its sheet became "Untitled 4".
- **Left behind:** `run.sh` then killed soffice.bin 1714360 with four unsaved documents (`leftover.txt`), so the next run, 20261024-170743, started in recovery again.
- **Still open:** Problem 5 of the 20261024-142622 report, not yet fixed. Give LibreOffice a per-run profile (`-env:UserInstallation=…`), or clear `user/backup` and `RecoveryList` before and after the run, and close LibreOffice gracefully before killing it.

### 6. `set_text` on the Name Box doesn't commit it, and the description doesn't say so (description gap, minor)

- **What happened:** at +81.8 the agent sent `set_text "A2:C50"` on the Name Box text (a139) and, in parallel, `press_window Enter`. The keyboard was still in the sheet, so Enter moved the cursor to A4, and the Name Box went back to "A4".
- **The fix the agent found:** `act_window focus`, then Ctrl+A, then `type_window "A2:C50\n"`, worked at +86.4 and +95.7.
- **What the description says:** `"set_text" (replace an editable text's contents with text)`. It doesn't say that the keyboard stays where it was, or that a field which acts on Enter needs focus first.
- **Suggested addition:** "set_text doesn't move the keyboard: to commit a field that acts on Enter, focus it and press Enter."
