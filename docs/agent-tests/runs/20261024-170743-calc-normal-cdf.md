## Problems

### 1. `read_window` on LibreOffice's untitled message box: "This app isn't on the accessibility bus" (tool bug)

What happened:

- **+45.0:** `read_window {"window_id":3}` failed: "This app isn't on the accessibility bus: it has no accessibility support, or it's off … Use snapshot_window instead."
- **+45.2:** `read_window` #2, the same process, worked.

What #3 was:

- Not a splash. It's LibreOffice's GTK message box "Are you sure you want to discard the LibreOffice document recovery data?" with No / Yes (`seen/002`, 933×286 snapshot pixels; `list_windows`: title "", 524×160).
- It is LibreOffice's answer to the agent's Escape on the recovery dialog (+27.3).
- A GTK dialog of an app whose other windows read fine has an accessibility tree, so this is a real failure.

Cause (`helper/src/a11y.ts`, `frameOf`, lines 245–320):

- **Own apps by pid.** It first looks among the accessibility apps whose D-Bus connection pid equals the window's pid (`own`). For a Flatpak app, the connection on the a11y bus comes from the sandbox's `xdg-dbus-proxy`, which is pid 1736506 in `leftover.txt`, not soffice.bin 1736565. So `own` is empty, I believe. That's inferred from the code and the process list; I haven't checked it on the bus.
- **Other apps by title.** It then matches frames of other apps by title only. That's how every titled LibreOffice window was found in both of today's runs.
- **#3 has no title,** so nothing matches. With `own` empty, it throws the "isn't on the accessibility bus" error.

Suggested fix:

- Count an a11y connection as the app's own when its pid is in the same sandbox as the window's pid: the same bwrap parent or Flatpak instance (`/proc/<pid>/root`, or `.flatpak-info`'s instance id). Then the size and active-frame fallbacks work for untitled windows too.
- Failing that, try untitled frames by size across all apps.
- Make the message honest when other windows of the same pid were found: "couldn't find this window in the app's accessibility tree".

Also affected: any untitled dialog of a Flatpak or other sandboxed app.

### 2. `act_window` "select" on "Line" in the chart type list: "The app refused to select it." (tool bug, on top of a toolkit limitation)

What happened:

- **+127.9:** `act_window {"window_id":8,"ref":"a27","action":"select"}` failed in 0.0 s. The ref differs from run A only because the tree's numbering shifted.
- **+131.7:** `click_window` at (535,333) selected Line (`seen/005`).

This is the same as Problem 1 of `20261024-170421-calc-normal-cdf.md`:

- `select` asks the parent table for `Selection.SelectChild` (`a11y.ts:707`).
- GTK3's tree-view accessible declines on multi-column views. This list has an icon column and a text column.
- The tool then reports the refusal instead of clicking.

Fix: fall back to a pointer click at the element's center, not `DoAction` (these cells' first action is "Expand or contract").

### 3. One of two Tabs in a row was dropped (tool or app, unexplained)

What happened:

- **+80.8:** `type_window "index\tx\tCDF\t\tmean\t100\n"` on A1.
- **Result** (`seen/004`, +85.5): "mean" landed in D1 and 100 in E1. Expected E1 and F1, so one Tab of the `\t\t` pair had no effect.
- **The rest:** row 2's `E2\nsd\t16\n` went to the right cells.

Keys go to Exo back to back, in batches with no gap between strokes (`helper/src/daemon.ts:1100`–`1117`, `textKeys` in `keys.ts:118`). LibreOffice may still be committing C1 when the second Tab arrives. The 2026-10-23 manual run saw a related Tab problem (a skipped column).

What would tell, on an empty sheet:

- `type_window "a\t\tb"`, then the same with `press_window ["Tab","Tab"]`, which has gaps between key combos.
- If only the back-to-back version fails, `textKeys` needs a short pause after a key that commits a cell (Tab, Enter), as Problem 4 of 20261024-142622 suggested for `\n`. That would make it a tool bug.

### 4. The shared LibreOffice profile: crash recovery again, and an a11y click past a modal box (app or environment: test harness)
