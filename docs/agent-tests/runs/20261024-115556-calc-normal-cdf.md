## Problems

### 1. The Flatpak LibreOffice's window never reaches the thread (tool bug, cause not yet located)

What happened: at 22:56:19 `launch_app ["org.libreoffice.LibreOffice","--calc"]` started the Flatpak through its export (`/var/lib/flatpak/exports/bin`). The helper (pid 532782, `plutonium.ts daemon --wayland-display wayland-plutonium … --cdp-port 9224`) spawned it as pid 655061. The tester's `ps` at 22:57:07 shows the chain `bwrap` 655061 → `bwrap` 655080 → `oosplash --calc` 655086 → `soffice.bin --calc` 655137. `launch_app` waited the full 45 s and returned no windows; `list_windows` stayed `[]` up to 22:57:22.

Verified:

- **The thread tag reached the app.** The orchestrator's capture of soffice.bin's environment: `PLUTONIUM_THREAD_ID=t3:thread/mcp:6c58e9bb-…`, `PLUTONIUM_HELPER=…/wayland-plutonium.sock`, `WAYLAND_DISPLAY=wayland-plutonium`, `XDG_RUNTIME_DIR=/run/user/1000`, no `DISPLAY`. The environment is readable from the host as the same user. The orchestrator read it, and Chromium and the helper read the tag the same way, from `/proc/<pid>/environ`.
- **Flatpak granted the Wayland socket.** The app's metadata has `sockets=cups;fallback-x11;pulseaudio;wayland;` and there are no overrides for it. `/run/user/1000/wayland-plutonium` exists as a socket. Flatpak keeps `WAYLAND_DISPLAY` names that start with `wayland-`. It drops `DISPLAY` only under `fallback-x11` when it found the Wayland socket. So the missing `DISPLAY` is consistent with the sandbox having Plutonium's Wayland socket, and X11/Xwayland isn't involved.
- **LibreOffice wasn't stuck at a first-start or recovery stage.** The Flatpak profile has `FirstRun=false`, `ooSetupLastVersion=26.8` (the installed 26.8.0.3) and no `RecoveryList`. `registrymodifications.xcu` was rewritten at 11:56:21 local, 2 s after launch, so startup ran normally. No other Flatpak LibreOffice instance was running that could have taken the start through `org.libreoffice.LibreOfficeIpc0`. The only other soffice was the Nix build from another thread (550468).
- **How a window gets to a thread** (code):
  - Exo records the client's pid from `wl_client_get_credentials` (`chromium/patches/0002-…-report-Wayland-client-pid…`).
  - `ExoWindowBroker::UpdateWindow` holds a new window back until `plutonium_tags::ReadThreadTag(pid)` has read `PLUTONIUM_THREAD_ID` from the client's `/proc/<pid>/environ`, walking up its parents (`chromium/patches/0014-…`).
  - If the pid is 0, or the client's environment can't be read, the window is added anyway with `tags = []`. In the second case it also logs `EXO-TAGS can't read window #N's client environment` at VLOG(1).
  - The helper's `threadWindows` (`helper/src/daemon.ts:464`) filters on `entry.tags.includes(threadId)` and only falls back to `threadForPid` when `tags` is missing. In direct (CDP) mode `tags` is always an array, so that fallback never runs. That includes `rememberLaunch`'s record of pid 655061, which `threadForPid` could have found by walking up from soffice.bin.

Not verified: whether a window opened at all, and if it did, what pid and tags Exo gave it. The logs can't tell. The helper log got nothing during the run, because the helper doesn't log `/v1/launch`. The Ash log for 22:56–22:57 has only `external_metrics` noise, because Ash isn't running with VLOG(1) for `exo_window_broker.cc`, so the `EXO-BROKER window added: … pid=…` lines are missing.

From the code, a soffice.bin window on `wayland-plutonium` with pid 655137 would have been tagged with this thread. So it's one of these:

- (a) No toplevel was mapped. soffice.bin connected but never showed a window, or never connected.
- (b) Exo got a pid other than 655137, or 0. For example, if Exo supports `wp_security_context_v1` and Flatpak 1.18.1 used it, the credentials might come from a different process.
- (c) The tag read failed in Ash but not in the orchestrator's shell (for example, Ash's own sandboxing).

soffice.bin had 4 socket fds and 1 s of CPU at 22:57:07. That fits a started instance waiting on events, but it doesn't settle (a).

What would tell, in one rerun with the process left running:

1. Start Ash with `--vmodule=exo_window_broker=1,plutonium_groups=1` and look for `EXO-BROKER window added: … pid=…` and `EXO-TAGS can't read window …`.
2. Ask the browser over CDP (port 9224) for all windows, not just the thread's, and look for an untagged LibreOffice window and its pid.
3. Run `ss -xp | grep 655137` (or the new pid) to see whether one of its sockets is connected to Ash's `wayland-plutonium` listener.
4. Run `wayland-info` on `wayland-plutonium` for `wp_security_context_manager_v1`, and/or launch with `flatpak run --env=WAYLAND_DEBUG=1 org.libreoffice.LibreOffice --calc`.
5. Take a screenshot of the desktop or the shell's Elsewhere list.

Suggested fixes, once the cause is known:

- If it's (b) or (c): in `threadWindows`, fall back to `threadForPid(entry.pid)` (with `launched` ancestry) when `tags` is empty, or have the helper name the origin through the existing `SetOriginTag` path.
- If it's (b): look the pid up through the Flatpak instance (`/run/user/1000/.flatpak/<instance>/bwrapinfo.json` maps an instance to its pids).
- Either way: log launches and each new window's pid and tags in the helper, so the next run's logs answer this directly.

### 2. `launch_app` can't start an app by its desktop name, and its description implies `libreoffice` works (missing capability + description gap; environment underneath)

What happened: at 22:56:12, `launch_app ["libreoffice","--calc"]` → `Could not start libreoffice: spawn libreoffice ENOENT`. The tester then used Bash (22:56:14, 22:56:16) to find the Flatpak and its export name. That was a reasonable discovery step, not a workaround.

The description the tester saw (T3's server, from the transcript; the run's `tools.json` only holds call counts and timings, not descriptions):

> Start a native desktop (GUI) app, such as LibreOffice, GIMP, Inkscape, a terminal or a file manager, as part of this thread, and wait for its window. … Returns the new windows (empty if none appeared in time).

`argv`: `Program and arguments, e.g. ["libreoffice", "--writer"]. No shell is involved.`

It names LibreOffice and gives `["libreoffice", …]` as the example. It says nothing about how `argv[0]` is found: it's resolved on the helper's PATH by `spawn` (`helper/src/daemon.ts` `launch`). Nor does it say that Flatpaks are reachable only by app id (`org.libreoffice.LibreOffice`), or that there's no lookup by app or `.desktop` name. The helper's own MCP description (`helper/src/mcp.ts:59`) doesn't say either.

On this machine LibreOffice is a Flatpak, plus a Nix store build that isn't on PATH. That makes it an environment fact. But the scenario names "LibreOffice", so any agent will hit this.

The helper already has what's needed:

- `helper/src/apps.ts` reads the desktop entries, including `/var/lib/flatpak/exports/share`.
- `GET /v1/apps` lists them.
- `POST /v1/apps/launch {thread, id}` starts one by desktop id (`helper/src/daemon.ts:1369`, `:1435`).

But only the user's launcher uses these. No agent tool lists apps or launches by desktop id.

Suggested fixes:

- Add an `app` (desktop id or name) alternative to `argv` in `launch_app`, plus a way to list installed apps, both backed by `/v1/apps`. This should go in both the helper's and T3's MCP definitions.
- Make the description say that `argv[0]` is looked up on PATH, and that names on PATH can differ from app names (Flatpak ids).
- When the program isn't found, have ENOENT suggest matching desktop entries ("not on PATH; installed: LibreOffice Calc (org.libreoffice.LibreOffice.Calc)").

Same as the known issue ("`libreoffice` isn't on PATH"): still failing.
