# What pages see: Linux Chromium, not ChromeOS

Plutonium is built as ChromeOS (Ash and Exo live there), but a page shouldn't be able to tell (`ARCHITECTURE.md`, "ChromeOS is an implementation detail"). Some sites serve ChromeOS their own UI, or break, when they see it.

## Fixed

- **The user agent** is `Mozilla/5.0 (X11; Linux x86_64) … Chrome/<major>.0.0.0 Safari/537.36`, as Linux Chromium's, not `X11; CrOS x86_64 14541.0.0`. UA client hints say platform `"Linux"` (`Sec-CH-UA-Platform`, `navigator.userAgentData.platform`), with an empty platform version, not `"Chromium OS"` and `24.4.0`. The OS/CPU string (the non-reduced UA) is `Linux x86_64`. Patch "pages see Linux, not ChromeOS" (`components/embedder_support/user_agent_utils.cc`, and its unit test's ChromeOS expectations). `navigator.platform` was already `Linux x86_64`.
- **The timezone** was UTC (the container's), so pages' clocks were off. Ash now gets the host's zone as `TZ` (`timedatectl`, else `/etc/localtime`), and `LANG`, from `lib/session.sh`, on every launch path. `Intl` and `Date` show the host's zone.
- **Languages** were `["en-US"]`; with `LANG` they are `["en-US", "en"]` as on Linux (`navigator.languages`, `Accept-Language`).
- **Web APIs ChromeOS has and desktop Linux Chromium doesn't** are off, as in Linux Chromium: Web Share and Web Bluetooth in the renderer (the UA patch), HandwritingRecognition and BarcodeDetector by turning off the base features Blink copies them from (`--disable-features`, from `lib/session.sh`). First done with `--disable-blink-features`, which showed Chrome's "unsupported command-line flag" infobar (it's on Chrome's list of bad flags); turning the two off in the renderer alone didn't hold, since Blink copies their base features' state after. Verified on Xvfb (build of 0055): all four `undefined`, and no flag from Chrome's list on Ash's command line: `navigator.share`/`canShare`, `navigator.createHandwritingRecognizer`, `BarcodeDetector`, `navigator.bluetooth`. A site seeing them on a Linux user agent could tell.
- **H.264 and AAC** (`proprietary_codecs = true`, `ffmpeg_branding = "Chrome"` in `chromium/args*.gn`, as nixpkgs' Chromium). Verified 2026-10-26 on Xvfb: `canPlayType` says `probably` to `avc1.42E01E` and `mp4a.40.2`, MSE and WebCodecs accept them, and a 320×240 H.264/AAC mp4 (made with ffmpeg) plays in a tab (frames presented, audio decoded). A tab no shell shows is hidden, and like Chrome's background tabs it doesn't load media until it is shown.

Verified 2026-10-26 on Xvfb with the build of the UA patch (0055), in a tab on example.com: `navigator.userAgent` `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/158.0.0.0 Safari/537.36`, `navigator.platform` `Linux x86_64`, `userAgentData` platform `"Linux"`, `platformVersion` `""`, architecture `x86`, timezone `Pacific/Auckland`, `navigator.share` and `navigator.bluetooth` undefined.

## How it was compared

`navigator`, `window` globals, `userAgentData` (with the high-entropy values), codecs (`canPlayType`), media capabilities and devices, fonts, WebGL strings, `window.chrome`, timezone and languages, read by one script in a Plutonium tab and in Linux Chromium (nixpkgs, 147, `--headless=new`) on a localhost page. Differences that come from the versions (158 against 147: `HTMLCameraElement`, `cpuPerformance`, `globalPrivacyControl`, …) or from headless (no WebGL) aren't listed.

## Fixed since

- **Fonts** (2026-10-27): pages and shells render with the host's fonts and fontconfig, as Linux Chromium does there. `plutonium container create` mounts the host's `/etc/fonts` and the font directories it names (`/usr/share/fonts`, `/usr/local/share/fonts`, and on NixOS `/nix/store`) read-only, over the image's; each session's `FONTCONFIG_FILE` (`$DATA_DIR/fonts-<socket>.conf`) includes that and adds your own fonts (`~/.local/share/fonts`, `~/.fonts`) and `~/.config/fontconfig`, which the container's `$HOME` doesn't have. A container made before this keeps the image's fonts (135, DejaVu Sans), and the session log says to make it again (`podman rm -f <container>`, then `plutonium container create`). Checked on Xvfb in a new container: a host-only font (JetBrains Mono from the Nix store) and a user font (`~/.local/share/fonts`) are there; `sans-serif` is Liberation Sans (Chrome's Arial, through the host's aliases) and `system-ui` Noto Sans, as in Linux Chromium on this host.
- **Dark mode** (2026-10-27): `prefers-color-scheme` in shells and tabs is the host's. The helper reads the settings portal's `org.freedesktop.appearance` `color-scheme` (GNOME, KDE and others set it) and watches `SettingChanged`; without a working portal, GNOME's dconf key (`/org/gnome/desktop/interface/color-scheme`, `dconf watch`). It sets Ash's dark mode (`Plutonium.setColorScheme`, the user's `ash.dark_mode.enabled`), which Ash carries to the web's native theme, on each change and each time the browser (re)connects. With neither, Ash keeps its own (dark). `PLUTONIUM_APPEARANCE_BUS` and `PLUTONIUM_DCONF` point it at a test's fake portal or dconf. Checked on Xvfb with a scratch dconf: the shell's `matchMedia("(prefers-color-scheme: dark)")` went from false to true as the value changed.
- **Web notifications from tabs** (2026-10-27): through the helper's notifications service, which the shells show ([DESKTOP_SERVICES.md](DESKTOP_SERVICES.md), notifications).
- **Media sessions over MPRIS** (2026-10-28, Chromium's tab features patch): the active media session (a tab's, the shells') is an `org.mpris.MediaPlayer2.chromium.instance<pid>` player on the session bus, as in Linux Chromium, so `playerctl` and other desktops' widgets see and control it. A ChromeOS build had `use_mpris` off and no `MediaKeysListenerManager`; both are on now, with `SystemMediaControlsLinux` on `dbus_thread_linux`'s session bus (the session passes `DBUS_SESSION_BUS_ADDRESS` into the container). Pages' media shorter than 5 s don't make a session, as in any Chromium. Ash still takes the hardware media keys. The helper's media service leaves this player out, as its "browser" player is the same session and knows the tab. As in Linux Chrome, losing the session bus ends the browser. Checked on Xvfb (slot 20): a shell page's 10 s tone with `MediaMetadata` showed in `playerctl -l` as `chromium.instance<pid>` with its title, artist and length; `playerctl pause`/`play` paused and resumed it; the helper's media state listed only `browser`.
- **Speech synthesis** (2026-10-28, Chromium's tab features patch): `speechSynthesis.getVoices()` lists the host's speech-dispatcher voices, and `speak()` speaks them, through Linux Chromium's `tts_linux.cc` (libspeechd, dlopen()ed). ChromeOS's platform TTS is ARC's, used only when ARC is there; TTS extensions' voices are listed as before, and off a ChromeOS device utterances no longer wait for its built-in eSpeak extension (which never comes). Like Linux Chromium it needs `--enable-speech-dispatcher`, which the session passes when the host has speech-dispatcher's socket (`$XDG_RUNTIME_DIR/speech-dispatcher/speechd.sock`, usually a socket-activated user unit; else it starts `speech-dispatcher --spawn -t 0`). Without it, no voices, as before. The runtime image has `libspeechd2`; the Nix package has `speechd-minimal` on its RUNPATH. `speak()` needs user activation, as in Chrome (`not-allowed` without). Checked on Xvfb against the host's socket-activated speech-dispatcher 0.12: 15232 voices (espeak-ng's voices × variants, pico, flite; the first, Afrikaans, is marked default, as on Linux), and an utterance's `start` and `end`.

## Still different (backlog)

- **IME**: Ash's input-method framework, not IBus/Fcitx. Native apps get it over text-input-v1 and v3 (`IME.md`).
- **Privacy Sandbox APIs** (Protected Audience, Shared Storage, fenced frames) are present in Linux Chromium 147 and not in ours; few sites look.
- **WebGL** reports ANGLE on Vulkan with the real GPU, like Linux Chromium with Vulkan; Linux Chromium's default is ANGLE on OpenGL, a different but not ChromeOS-specific string.
